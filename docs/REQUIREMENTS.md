# 머무름 (Stay Curator) PoC 요구사항

## 1. 문제와 목표

부부·가족 여행마다 여러 숙박 플랫폼을 반복 탐색하며 가격, 욕실 수, 편의시설, 수용 인원, 이동 거리 같은 정보를 다시 비교하는 시간을 줄인다. 서로 다른 원천의 숙소 정보를 공통 형식으로 정리하고, 여행 목적과 필수 조건에 맞는 후보를 한 화면에서 제안한다. 예약·결제는 하지 않고 원 플랫폼의 상세 페이지로 이동한다.

## 2. PoC 범위

### 포함

- 여행 목적을 선택하는 메인 화면, 조건 비교 탐색 화면, 향후 로그인/공급자 연결 관리 화면
- 사용자가 입력한 전국 지역을 대상으로 NAVER API HUB 공식 지역 검색 후보 수집(지역별 6개 질의, 최대 30건, 10분 캐시)
- 입력한 지역·체크인·체크아웃·인원이 반영된 에어비앤비 공식 검색 링크와 여기어때·야놀자·개인 호스팅을 가정한 **샘플 데이터 어댑터**
- 플랫폼별 필드가 다른 데이터를 공통 숙소 모델로 정규화
- 목적 프리셋: `둘만의 쉼`, `가족 여행`, `친구들과`
- 검색 조건: 지역, 체크인, 체크아웃, 숙박 인원
- 필터: 1박 최대 가격, 최소 욕실 수, 최소 평점(기본 4.5), 편의시설
- 편의시설: 욕조, 편백, 사우나, 수영장, 바비큐, 반려동물
- 현재 위치 기준 예상 이동 거리/시간 표시(샘플 좌표 기반 직선거리 보정치)
- 조건 일치도 기반 추천 점수와 추천 이유
- 가격/거리/추천순 정렬
- 숙소 카드, 찜(localStorage), 상세 정보 모달, 원문 링크
- 반응형 웹 UI 및 접근 가능한 키보드 조작

### 제외

- 실시간 재고·최종 결제 가격·예약 가능 여부 보장
- 실제 플랫폼 로그인, 결제, 예약
- 네이버 별점 필터(지역 검색 API가 별점 필드를 제공하지 않음)
- NAVER 결과의 실제 가격·재고·사진 표시(지역 검색 API 미제공)
- 비공개 API 호출이나 로그인 세션/쿠키 우회
- 플랫폼 웹페이지의 무단 자동 수집
- 실제 주소 기반 정밀 경로 탐색

## 3. 핵심 사용자 시나리오

1. 사용자가 여행 목적을 선택한다.
2. 전국 지역과 날짜를 입력하고 예산, 욕실 수, 인원, 최소 평점, 편의시설을 지정한다.
3. 여러 플랫폼의 숙소가 동일한 카드 형식으로 정렬되어 나타난다.
4. 사용자는 추천 이유, 거리, 핵심 조건, 데이터 갱신 시각을 비교한다.
5. 상세 정보에서 원문 링크를 눌러 해당 플랫폼에서 최신 정보와 예약 가능 여부를 확인한다.

## 4. 기능 요구사항

| ID | 요구사항 | PoC 수용 기준 |
|---|---|---|
| FR-01 | 다중 원천 정규화 | 서로 다른 필드명의 입력을 공통 모델로 변환한다. |
| FR-02 | 복합 필터 | 선택된 모든 필수 조건을 AND로 적용한다. |
| FR-03 | 목적별 추천 | 목적별 가중치와 숙소 특성으로 0~100 점수를 계산한다. |
| FR-04 | 설명 가능한 추천 | 카드에 점수에 기여한 추천 이유를 최대 3개 표시한다. |
| FR-05 | 비교 가능한 표시 | 가격, 욕실, 인원, 거리, 편의시설을 모든 카드에 동일하게 표시한다. |
| FR-06 | 원문 이동 | 상세 페이지는 새 탭에서 열리고 외부 이동임을 알린다. |
| FR-07 | 찜 | 브라우저를 새로 열어도 찜 상태가 유지된다. |
| FR-08 | 빈 결과 | 조건 완화 방법과 초기화 버튼을 제공한다. |
| FR-09 | 데이터 투명성 | 샘플/제휴/API 등 데이터 출처와 갱신 시각을 표시한다. |
| FR-10 | 목적 진입 | 메인 화면에서 부부/가족 여행 목적을 선택해 탐색 조건으로 전달한다. |
| FR-11 | 공급자 연결 | 로그인과 공급자 API/공식 링크 상태를 별도 화면에서 구분해 표시한다. |
| FR-12 | API 예산 | 네이버 자동 수집은 기본 6회 호출, 최대 30건, 10분 캐시로 제한한다. |
| FR-13 | 날짜 검색 | 체크아웃이 체크인보다 늦도록 검증하고 에어비앤비 공식 검색 링크에 날짜·인원을 전달한다. |
| FR-14 | 전국 지역 검색 | 최대 40자의 지역 입력을 정규화해 지역별 NAVER 검색어를 생성하고 지역/숙박 업종을 검증한다. |
| FR-15 | 평점 게이트 | 실제 평점이 있는 데이터만 최소 4.5 조건을 적용하며, 평점 미제공 NAVER 결과는 미검증 후보로 분리한다. |
| FR-16 | 미제공 이미지 | 이미지 권한이 없는 실데이터에는 가짜 사진 대신 `사진 미제공` 상태와 원문 확인 경로를 표시한다. |
| FR-17 | 입력 경계 | 날짜 쌍·인원·평점·target·의미 있는 지역을 서버에서 엄격 검증하고 잘못된 요청은 400으로 거부한다. |
| FR-18 | API 예산 보호 | NAVER fetch는 프로세스 전체 동시성 3, 검색 API는 IP별 10회/분으로 제한한다. |

## 5. 공통 데이터 모델

- `id`, `source`, `sourceLabel`, `sourceUrl`
- `name`, `location`, `coordinates`
- `pricePerNight`, `capacity`, `bathrooms`, `bedrooms`
- `amenities[]`, `tags[]`, `image`
- `rating`, `reviewCount`, `verified`, `updatedAt`

표시 가격은 비교용이며, 세금·수수료·성수기 변동을 포함한 최종 가격은 원 플랫폼에서 확인한다.

## 6. 비기능 요구사항

- 별도 빌드 없이 Node.js 정적 서버로 실행 가능한 웹 PoC
- 외부 런타임 라이브러리 없이 동작
- 도메인 로직에 대한 Node 내장 테스트 제공
- 모바일 360px 이상, 데스크톱 화면 대응
- 키보드 포커스, 의미 있는 레이블, 충분한 색상 대비 제공
- 플랫폼 하나의 장애가 전체 검색을 막지 않는 어댑터 구조

## 7. 정책·법률·운영 리스크와 제안

> 법률 자문은 아니며 출시 전 국내 변호사 및 각 플랫폼의 제휴/API 담당자 검토가 필요하다.

1. **서비스 약관/자동 수집**: 로그인 뒤 화면을 크롤링하거나 CAPTCHA·접근 통제를 우회하면 약관 위반 및 법적 분쟁 위험이 있다. 공개·공식 API, 어필리에이트 피드, 개별 숙소의 서면 동의를 우선한다.
2. **데이터베이스권·저작권**: 숙소 설명, 사진, 후기와 데이터 배열은 보호될 수 있다. 원문을 대량 복제하지 말고, 라이선스가 확인된 썸네일과 사실 정보의 최소 범위만 표시하며 상세는 딥링크한다.
3. **상표/오인 가능성**: 플랫폼 로고·색상·UI를 모방하지 않는다. 출처명은 사실상 식별에 필요한 범위로 쓰고, 비제휴 상태라면 명확히 고지한다.
4. **개인정보/통합 인증**: 플랫폼 비밀번호를 직접 수집·보관하지 않는다. 제공되는 OAuth/OIDC만 사용하고 최소 권한, 암호화, 탈퇴·토큰 폐기 절차를 둔다. 현재 위치는 명시적 동의를 받고 가능하면 브라우저 안에서 계산한다.
5. **가격 표시**: 수수료·세금·환율·날짜별 가격 때문에 오인 가능성이 있다. 갱신 시각과 ‘예상/비교용’을 표시하고 최종 가격은 원문에서 확인하도록 한다.
6. **추천 투명성**: 광고·제휴 수익이 순위에 영향을 주면 ‘광고/제휴’로 분리 표기하고 자연 추천과 섞지 않는다.
7. **링크 정책**: 각 플랫폼의 딥링크·어필리에이트 정책과 robots.txt를 확인한다. 삭제/수정 요청과 데이터 정정 창구를 운영한다.

## 8. 실서비스 단계 제안

1. 네이버 검색/지도, 공식 관광 데이터 등 허용된 공개 API로 1차 연동
2. 개별 숙소 직접 등록 및 소유권 인증
3. 플랫폼별 제휴/어필리에이트 계약 후 가격·재고 피드 연결
4. 출처별 TTL, 중복 숙소 병합, 품질 점수, 삭제 요청 워크플로 추가
5. 개인정보 영향평가, 이용약관/개인정보처리방침, 추천·광고 표시 정책 확정
